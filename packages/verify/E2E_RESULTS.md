# Cross-chain verification (Oct 3, 2026 — hardened verifier)

`receptum-verify` returns **VERIFIED** only when nothing fails, is pending or is unavailable, the delivered file matches (L1), the seller signed the receipt (L2), the seller is proven to control the payee (L2.5, SPEC §4.1), the payment itself is confirmed on its rail **and** `receiptHash` is committed on-chain — by the escrow rail itself, or by a mined anchor for x402 (SPEC §6); **NOT VERIFIED** when any check fails; **PARTIALLY VERIFIED** otherwise, with the missing pieces listed.

**Re-evaluated under the SPEC alignment (2026-10-03).** VERIFIED now also requires the delivered file and, for x402, an anchor. Only the Base Sepolia x402 receipt publishes both its delivered bytes and an anchor, so it is the only published receipt that reaches VERIFIED. The escrow receipts below pass every level they can — signature, binding, settlement and the committed `receiptHash` — but their delivered files were not published, so without the file they are PARTIALLY VERIFIED (`missing: L1`). The Stellar x402 receipt publishes its delivered file but was never anchored, so it is PARTIALLY VERIFIED (`missing: … receiptHash is not committed on-chain`). The receipts and their hashes are unchanged.

**Account bindings (re-run 2026-10-03).** The x402 receipt was re-issued with a binding and verifies in full including L2.5; the XRPL escrow A and Arc escrow A receipts carry bindings attached afterwards (`examples/xrpl-testnet-escrow-a.json`, `examples/arc-testnet-escrow-a.json`) — XRPL after the switch to chronological delivery derivation (first seller memo after `EscrowCreate`). Without a binding a receipt with a payee is `PARTIALLY VERIFIED`; `--allow-unbound` skips L2.5 for legacy receipts. See [examples/E2E_RESULTS.md](../../examples/E2E_RESULTS.md).
